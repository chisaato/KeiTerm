# Dock 单窗口多连接分屏工作区设计规约

## 1. 概述与背景

KeiTerm 现阶段主窗口采用扁平的单标签栏与单终端展示区（`ItemsControl` + 依据 `IsSelected` 切换可见性），终端控件 `TerminalControl`（基于 RoyalApps.RoyalTerminal.Avalonia 0.6.0-preview.2）由 `TerminalTabViewModel.Control.cs` 内部惰性创建并强持有，所属 SFTP 文件管理侧栏（`RemoteFileManagerView`）以内嵌在同一标签网格的方式共存。

随着多服务器运维操作的深入，用户提出了**单窗口内多连接分屏平铺对照**（如同时观测两台服务器日志或跨主机文件对比）的核心需求。在本次设计边界中，确定了以下最高优先级的体验与技术约束：
1. **舒适操作与整体联动**：一个会话连接下的 Shell 终端与所属 SFTP 侧栏作为**不可拆分的原子整体（Connection Unit）**移动与停靠，不单独拆分 SFTP 独立成窗格，先验证双连接及多连接并排/上下分屏的组合效果。
2. **免浮动与专注单窗口**：不引入独立浮动桌面窗口，不涉及跨窗口拖动；不引入代码编辑器；聚焦终端与文件管理的纯粹分屏。
3. **标签层级清晰，拒绝双层标签套娃**：每个窗格组（Pane Group）只展示一层连接标签（展示该组所容纳的连接集合），不出现内部二级 "Shell / SFTP" 标签栏；全局标签位置遵循现有配置（Top 或 Bottom），统一作用于各组。
4. **生命周期绝对安全**：隐藏、折叠、拖拽换组、分屏调整过程中，**严禁触发底层 SSH 连接断开、SFTP 重新建立或终端控件重新实例化**。
5. **设计交付阶段边界**：本规约立足技术可行性与交互规范，当前设计交付阶段严格禁止引入依赖、修改产品代码或执行 git 写操作；待本设计经主会话审核并获用户批准后，后续实施阶段才允许依照获批计划执行代码与依赖修改。对停靠库（如 `wieslawsoltes/Dock`）采用严谨的探针验证原则，设计不作未核实断言。

## 2. 交互模型与分屏文字示意

### 2.1 窗格组（Pane Group）与活动状态模型
- **窗格组（Pane Group）**：主工作区被分割为一至多个互不重叠的矩形视口。每个窗格组在视觉上由一个**连接标签栏（Tab Strip）**和下方的**活动连接内容区（Host Content Area）**组成。
- **活动窗格组（Active Pane Group）**：全局在任一时刻有且仅有一个获得焦点的活动组。
  - 用户点击某个窗格组内的标签、Shell 终端、**或在其所属 SFTP 侧栏内点击/交互**，该组即被立即激活为当前活动组。
  - 新建连接默认落入当前的活动窗格组。
- **共享撰写栏与活动组防误发**：
  - 主窗口底部为全局共享撰写栏（Compose Bar）。
  - 当焦点由终端移入共享撰写栏输入命令时，**必须保留进入前的最后活动组与最后选中连接**，避免因终端失焦导致活动目标重置或清空而引发命令误发。
- **组内选中连接（Active Tab in Group）**：每个窗格组内可容纳 1 至多个连接单元。组内有且仅有一个当前选中的连接（`Group.SelectedTab`），该连接的 Shell 与 SFTP 在内容区呈现。
- **全局选中连接（Global SelectedTab）**：`MainViewModel.SelectedTab` 始终与活动组的 `SelectedTab` 保持同步，主窗口顶部工具栏状态（如断开按钮、文件管理器切换开关）及底部撰写栏以此为准。

## 3. 连接标签拖拽与分屏交互手感

### 3.1 拖拽触发与防抖阈值
- 沿用目前 `MainWindow.axaml.cs` 中经实践验证的交互阈值：
  - 鼠标左键按下（`PointerPressed`）在标签项上，记录起始坐标 `_dragTabStart`。
  - 鼠标移动超过 **6px**（欧氏距离 $\sqrt{\Delta x^2 + \Delta y^2} \ge 6$）时，启动拖拽传输（`DoDragDropAsync`）。
  - 中键点击直接关闭标签；点击 `✕` 关闭按钮拦截冒泡，不触发任何拖拽。

### 3.2 停靠落点指示与放置区域（Drop Targets & Visual Feedback）
- 停靠判定遵循 Dock 框架的提示目标与可视指示层（Drop Compass / Dock Adorner），避免在设计期硬编码未经验证的百分比阈值，以消除边缘与角落命中判定重叠：
  1. **组内重排（Tab Reorder）**：悬停在目标标签栏的标签项之间，呈现插入竖线指示符（Insert Indicator），松手后在当前组内调整索引位置。
  2. **加入已有组（Merge into Group）**：拖拽至已有窗格组的标签条空余区域或视口中心停靠目标，松手后该连接加入该组末尾并成为该组的活动连接。
  3. **窗格边缘分屏（Split Group）**：
     - 当拖拽移动至目标窗格并命中外围停靠向导指示目标（上/下/左/右停靠靶点或经 Dock 几何计算的目标边缘）时，视口显示对应区域的半透明高亮遮罩。
     - 具体判定阈值、向导图标尺寸与内外边缘响应范围在后续依赖引入与原型核验时结合所选停靠库的具体 API 规范确定，杜绝硬编码冲突。
     - 松手后触发对应方向的分屏（Split Left / Right / Top / Bottom），原窗格与新生成窗格平分当前视口空间。

### 3.3 拖出窗口行为与安全取消
- **非目标策略**：本次迭代严格禁止分离出独立的桌面原生窗口（No Floating Windows）。
- **取消机制**：当标签被拖出主窗口有效视口外，或者用户按下 `ESC` 键，或者拖拽松开在无效区域时：
  - 立即终止拖拽（`DragEffects.None`）。
  - 标签原地复原，不改变所属组与顺序。
  - 界面不出现任何瞬时闪烁或未处理异常。

## 4. 连接整体性与 SFTP 状态保持

### 4.1 Shell + SFTP 作为一个原子单元
- 连接单元定义为 `TerminalTabViewModel`。其内部状态属性包括：
  - `TerminalControl Terminal`：终端物理实例。
  - `RemoteFileManagerViewModel? FileManager`：所属 SFTP 视图模型。
  - `bool IsFileManagerVisible`：SFTP 侧栏展开/收起状态。
  - `bool IsFileManagerOnLeft`：SFTP 停靠方向（左侧或右侧）。
- **原子迁移**：标签拖拽搬迁的不仅是 Shell 视口，而是承载 `TerminalTabViewModel` 的完整数据上下文。当该连接从组 1 移动至组 2 时：
  - 其 SFTP 是否展开、展开宽度、停靠在左还是右、当前浏览的远端目录与本地目录路径、文件传输队列全部保持原样不变。
  - 绝不重新连接 SFTP 客户端，不重新发 SSH 认证请求。
- **组激活联动**：用户点击 TerminalControl 固然激活所属组，点击 SFTP 内部任何控件（如目录树、文件列表、路径栏）同样将所在窗格组置为活动组。

### 4.2 视觉布局与设计规范沿用
- **内层结构**：窗格内容区沿用当前 `MainWindow.axaml` 经过生产验证的 Grid 布局：
  - Column 0: 终端或 SFTP（取决于 `IsFileManagerOnLeft`，使用 `FileManagerDockConverter`）
  - Column 1: `GridSplitter`（宽 4px，背景 `{DynamicResource Kei.Bg.PanelAlt}`，仅在 `IsFileManagerVisible` 为 True 时显示）
  - Column 2: 终端或 SFTP
- **设计令牌继承**：严格复用 `KeiTokens.axaml` 与 `KeiControls.axaml` 定义的资源变量，如：
  - 边框与分割条：`{DynamicResource Kei.Border}`、`{DynamicResource Kei.Bg.PanelAlt}`
  - 背景：`{DynamicResource Kei.Bg.Window}`、`{Binding TerminalBackground}`
  - 标签指示色条：继承 `ConnectionState`（Connecting 橙、Connected 绿、Disconnected 灰、Error 红）。
- **单一层级标签**：各窗格组只呈现会话标签（如 `Server-1`, `Server-2`），绝不在窗格内部再增加“终端 / SFTP”的分页标签，SFTP 的展现完全由原生的侧栏展开按钮（工具栏或快捷键）控制。

### 4.3 标签栏位置复用（TabPlacement）
- 复用现有 `MainViewModel.TabPlacement`（`Top` / `Bottom`）全局选项。
- 当用户在设置中切换标签位置时，所有窗格组的标签条统一置顶或统一置底，各组内部样式与边框厚度（`Thickness(0,0,0,1)` vs `Thickness(0,1,0,0)`）统一联动响应，不提供混乱的“窗格 A 居顶、窗格 B 居底”局部差异。

## 5. 生命周期与资源管理契约

### 5.1 迁移与隐藏过程中的保活铁律
- **痛点场景**：在常规 Avalonia 控件树变换（如把 Visual 从一个容器 Remove 然后 Add 到另一个容器）或 `ContentControl` 切换 `Content` 时，Avalonia 会触发 `Visual.DetachedFromVisualTree` 和 `Unloaded` 事件。
- **保活承诺**：
  1. `TerminalTabViewModel` 及其底层的 `ITerminalSession`（基于 SSH.NET / SshDialer）、`ISftpClient` 必须常驻内存，生命周期完全由 ViewModel 决定，与 UI 控件树挂载状态解耦。
  2. 窗格折叠、分屏调整或在后台标签隐藏时，连接保持存活并持续在后台缓冲区写入 VT 数据流。
  3. 切换标签或分屏移动绝不调用 `tab.DisposeAsync()` 或断开网络 socket。

### 5.2 迁移清空组 vs 明确关闭的生命周期区分
必须严格区分“**连接跨组迁移导致的空组收拢**”与“**用户主动关闭连接**”的生命周期边界：
- **情况 A：跨组迁移清空原组**
  - 当组内唯一的连接被拖入其他组时，原窗格组变为空组并自动收拢销毁。
  - **被拖动的连接绝不能被 Dispose**，该连接必须无缝在目标组继续运行。
- **情况 B：用户明确关闭连接（Explicit Close）**
  - 仅当用户在标签栏点击 `✕` 按钮、按中键、或右键执行关闭命令时，才触发真正的关闭链路。
  - 从所在组移除后，若该组变为空组，收拢销毁该空组。
  - 主 ViewModel 统一调用 `tab.DisposeAsync()`，由其在后台任务中优雅断开 SSH 连接并释放终端原生句柄。
- **全空状态回退**：若所有组的所有连接均已明确关闭，主区域展示平整纯色背景（`Kei.Bg.Window`），底部撰写栏自动隐藏。

## 6. 技术架构选项与 RoyalTerminal 探针验证门槛

### 6.1 方案选型评估：`wieslawsoltes/Dock` 适配性
为避免从头手动编写复杂的 Grid 分割树与拖拽停靠层，业界成熟的 Avalonia 停靠框架为 `Dock.Avalonia`（由 Wiesław Šoltés 维护）。
- **现状与版本警示**：
  - KeiTerm 目前使用 **Avalonia 12.1.2** 与 **.NET 10**。
  - `Dock.Avalonia` 在 NuGet 上的公开发行版（如 11.x 系列）主要面向 Avalonia 11.x，针对 Avalonia 12.x / preview 或特定编译版本的二进制兼容性尚未在本项目核验。
  - **红线**：当前设计阶段不引入任何 NuGet 包，严禁在未经过真实探针验证前在规范中宣称 `Dock` 已完全适配或开箱即用。

### 6.2 RoyalTerminal 控件重挂载与焦点真实探针验证门槛
在决定全面引入任何 Dock 库或自定义分屏框架之前，**后续实施阶段必须首先通过一个最小可运行探针（PoC Spike）核验以下跨平台物理门槛**（注意：跨平台渲染管线在 Linux 下多走 Vulkan/OpenGL/Software，不假定 Direct2D 存在）：
1. **重挂载（Re-parenting / Detach-Attach）存活测试**：
   - 当 `TerminalControl` 在运行时从一个视觉容器移除并加入另一个容器时，Avalonia 底层渲染器（Linux/macOS/Windows 各平台对应后端）是否会出现黑屏、画面停滞或崩溃？VT 渲染引擎是否能无缝继续渲染？
2. **尺寸重算（Resize & PTY Rows/Cols）同步测试**：
   - 依赖 `TerminalTabViewModel.Control.cs` 中的 `OnTerminalSizeChanged` 与 `TrySyncTerminalSize()`（向 `_endpoint?.SetSize` 下发列宽行高）。
   - 分屏导致窗格物理宽度突变时，`TerminalResized` 事件与 `OnTerminalGridResized`（`AlignGridToBottom` 贴底计算）能否正确触发，保证 `htop` / `vim` 等全屏程序排版不乱？
3. **键盘焦点（Focus Management）流转测试**：
   - 点击任一窗格的终端控件后，Avalonia 焦点管理器是否能准确将键盘按键（特别是方向键、Tab、Ctrl 组合键）直接送达该 `TerminalControl`？从一个窗格切到另一个窗格时焦点是否顺畅流转？
4. **历史回滚缓冲（Scrollback Buffer）与滚动绑定保持测试**：
   - 包含在外部 `ScrollViewer`（`Classes="terminalScroll"`）中的终端实例（`TerminalControl` 实现 `ILogicalScrollable`），在分屏迁移或尺寸变动后：
   - 原有的滚动绑定必须保持有效，历史回滚缓冲区（Scrollback Buffer）内容完好无损，用户仍可正常滚动查看历史，**不要求且不应在移动或分屏时将滚动偏移强制归零**。

## 7. 布局状态与设置边界

1. **首次实验不持久化活会话与凭据**：
   - 由于多连接分屏处于实验阶段，且 KeiTerm 具有严格的凭据隔离规范（硬件密钥、会话密码不在磁盘留痕），应用冷重启时不保存、不自动恢复已建立的分屏 SSH 活会话。
2. **首次实验不持久化布局**：
   - 本次设计交付与首次分屏实验**不存储任何窗口布局状态**，不增加新的配置字段。
   - 至于是否在未来支持分屏几何记忆（如恢复分割比例），待首次分屏在真实使用中验证效果与手感后，再由主会话与用户评估决定，本期不作为审批的前置必须项。

## 8. 验收路径与非目标（Acceptance & Non-goals）

### 8.1 验收路径（用户实跑验证准则）
1. **单组基础**：启动应用，连接单个会话，终端与 SFTP 表现与基线完全一致，字号缩放与右键菜单正常。
2. **生成分屏**：打开第二个连接，将第二个连接标签拖拽至分屏目标区域（根据 Dock 停靠提示指引），界面无缝划分为左右两组，每组有各自的连接标签条。
3. **原子移动验证**：
   - 展开 Server-A 的 SFTP 侧栏，并进入某个目录。
   - 将 Server-A 拖入另一窗格组，Server-A 的 SFTP 仍然保持展开，目录路径未改变，Shell 会话未中断，无需重新输入密码。
4. **焦点与撰写栏联动**：
   - 点击左侧终端或 SFTP，底部撰写栏输入命令发送至左侧连接；点击右侧终端或 SFTP，撰写栏无缝对准右侧连接。
   - 点击进入底部撰写栏输入时，保持对准最后活动的窗格组连接，不发生目标漂移。
5. **空组销毁与保活区分**：
   - 若将某组仅有的一个标签拖到其他组，原空组自动销毁收拢，但该标签连接持续正常运行不中断。
   - 仅当明确点击标签 `✕` 关闭按钮关闭标签时，才释放该连接。
6. **取消拖出**：拖拽标签移出窗口边缘松手，标签原位保留，不产生浮动窗口，无任何闪退。

### 8.2 非目标（Strict Non-goals）
- ❌ **不支持浮动独立窗口（No Floating Windows）**：窗口外无独立停靠宿主。
- ❌ **不拆分单独 SFTP 窗格**：SFTP 始终依附于所属连接终端，不成为顶级分屏节点。
- ❌ **不内置代码编辑器（No In-app Editor）**。
